## 三、R38 钉死的 3 个根因（推翻了我原先的猜测）

### 问题 1：`/save` 误报「另一个实例正在写」并另存 `X (2)`

- **真根因**：轮末自动保存（`agent.py` 的 `on_auto_save`，narnat-agent 线程）与 `/save`
  （RPC 主线程）打在**同一个 `RootSession`** 上，两者读到**同一个旧 `_sig`**；
  先写的换掉文件后，后写的撞 `session_store.py:399` 的 `raced=True` → 另存 + 假警报。
  窗口 = 一次 `json.dump`（2MB ≈16ms）。确定性 3/3、自然时序 6/6、等 400ms 则 0/3。
- **不是**「另一个实例」（那句文案本身也是错的）。
- **也不是** R39 猜的「timestamp 无条件刷新」——那只是让 mtime 必然变，但真正判定用的是
  写入前校验（`raced`），与时间戳精度无关（时间戳实测：文件不动 1000 次 stat 只有 1 个值）。

### 问题 2：损坏会话在列表里彻底消失、点进去报「会话不存在」

- **真根因**：`list_sessions_tree_checked()` 对解析失败的文件静默 `continue`
  （`session_store.py:692-696`），`errors` 只收目录枚举失败；`resolve_session_name()`
  基于这棵「已跳过的树」，裸名永远匹配不到，**它自己**就返回「会话不存在」——
  所以 `_preflight_switch_target()` 里那段「带 load 原话」的代码**永远走不到**。
- **分界**：能解析成 dict 就可见（`messages` 非数组也可见，报真错）；读不成 dict 才彻底消失。

### 问题 3：`content` 非字符串 → 请求体非法 → 该会话永久发不出去

- **真根因**：`load_session()` 只校验 `messages` 是数组，**逐条 content 类型从不检查**；
  `_user_blocks()` 里 `text = content or ""` 之后直接把数字/布尔/字典塞进请求体。
- **真 API 实测是 422 不是 400**，用户吃到上游原始英文报文。
- **更隐蔽**：`content: 0` 被 `content or ""` 吞成空串 → **静默丢掉一条提问**，不报错。

## 四、本轮修了什么（4 处）

| # | 修的内容 | 层级 | 验证 |
|---|---|---|---|
| 1 | 斜体/删除线补 flanking 规则 | 前端 `markdownInline` | `regress-md-emphasis` 13 项 |
| 2 | `**粗体**` 允许内层单个 `*`（原来整条不匹配、连 `**` 都原样露出） | 前端 `markdownInline` | 同上 R12/R13（`strong=1 em=1` / `strong=2`） |
| 3 | `content` 一律规整成字符串（新增 `_as_text()`，两套协议共用） | 后端 `llm.py` | `xcheck-content-type` 20 项：5 种坏类型全部能正常对话 |
| 4 | 同一会话的「读指纹→写盘→写指纹」串行化（按名分片锁） | 后端 `session_callbacks.py` | `xcheck-concurrent-save` 7 项：0 个 `(2)`、0 假警报 |
| 5 | 损坏会话报「会话文件损坏…」而不是「会话不存在」 | 后端 `server.py` | R38 p2 脚本：文案已变，且给出具体错因 |

**修 3 的关键细节**：`_as_text` 的规则是「优先保内容」——
`0` → `"0"`（不再被吞）、`True` → `"True"`、列表 → 拼 text 块或 JSON、
字典 → JSON（`sort_keys` 保证同一份数据每次得到同一串，不吃掉上游缓存）。

**修 4 的关键细节**：锁必须把**读 `_sig`** 一起圈进来，只锁写没用；
锁按会话名分片（不能全局，否则保存 A 阻塞保存 B）；锁内只有一次 `json.dump`，
不碰 LLM / 压缩 / 命名。跨进程保护一点不退。

## 五、R39 发现但**不修**的一条

**每次 `session/switch` 都会重写「切走前那个会话」的文件**，唯一变化的字段是 `timestamp`
（`session_store.py:479` 无条件写 `time.time()`），字节 ±1B，sha1 每次变。

- 影响：无谓写盘；跨实例时会让对方看到指纹变化（但已由问题 1 的锁解决误判）
- 不修的理由：这是「切走前必须落盘」+「落盘必刷 timestamp」两条设计的叠加。
  要消除得让 `save_session` 在内容未变时跳过写盘——那是**行为变更**，
  风险大于收益（可能让"用户改了 status/summary 但消息没变"这类保存在不该跳的时候跳过）。
  **记录待裁决**。

R39 还如实指出我任务书里两条判据写错了（「文件新增只在 5/9/11」与
「反复切会话不改写文件」），并给了可解释版本 —— 这是正确的做法，判据错就报判据错。
