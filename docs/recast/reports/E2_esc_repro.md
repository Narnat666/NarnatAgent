## 1. 现象与任务目标

用户报告原文（逐字引用）：

> 我打开narnat程序，询问你好，然后立即按下`键和esc键，交替按，这个时候ui会一直显示思考中，无法打断，也没有输出，后续狂按esc也没有用
> 等待了一会，才显示打断了，即当用户想按esc打断的时候，先按错了一个键，后续又按esc就会出现这种问题
> 用户狂按esc，后续过了很久界面显示已打断

任务目标：在真实终端中复现上述操作序列、产出带时间戳的证据，并对照新旧实现判定影响范围。

## 2. 实验装置（黑盒、无需窗口焦点）

| 环节 | 实现 |
|---|---|
| 启动 | `cmd /c start "" [conhost] <python> main.py -d`，新控制台窗口；两种宿主：默认终端（实测为本机 Windows Terminal/ConPTY）与 `conhost.exe` 强制经典控制台 |
| 目标识别 | 启动前后 `python.exe` 进程差集 + 命令行含 `main.py` 匹配（`runner.py:wait_target_pid`） |
| 按键注入 | `AttachConsole(pid)` → `CreateFile("CONIN$")` → `WriteConsoleInputW`，每个按键发 keydown+keyup 两条 `KEY_EVENT`（VK 码 + UnicodeChar）；注入时刻由 `perf_counter` 精确控制到 ms 级（`winctl.py`） |
| 读屏 | `CreateFile("CONOUT$")` → `ReadConsoleOutputCharacterW` 读可见窗口逐行文本，间隔 ~20ms；变化帧与标记时刻全部落盘（`driver.py`） |
| 时间基准 | t0 = "回车" KEY_EVENT 注入完成时刻；注入与读屏在同一进程内完成，事件时刻可直接相减 |
| 配置隔离 | `NARNAT_HOME` 指向 `%TEMP%\narnat_esc_home_new` / `_old`（`.narnat` 配置副本）——主线工作树 `.narnat` 零写入，两版本日志互不覆盖 |
| 每 run 流程 | 启动目标 → 等提示符就绪 → 注入 Ctrl+C 清空残留编辑缓冲 → 注入"你好"+回车 → 按序列注入按键 → 采样至中断/完成 → `taskkill /F /T` 清理（含 conhost 残留）→ 归档 narnat 日志 |
| 序列间隔离 | 每条实验独立启动新进程（旧进程完全退出后再启动下一条），不与其它 narnat 并行 |

## 6. 数据观察与判定

1. **延迟双峰**：快路径 0.04–0.59s（24 次）与慢路径 2–11.5s（11 次）分离明显；慢路径中有 7 次集中在 11.2–11.6s。
2. **屏幕行为一致**：所有慢路径 run 均为"思考中动画持续刷新、无内容输出、期间按键不改变状态、最后一次性跳到'已打断'"——与用户描述逐字吻合。
3. **与"先按错键"的因果不成立**：慢路径同样出现在基线单 ESC、纯狂按等无错键序列；同序列重复时快慢混现（如交错连按 0.26/11.26/0.06）。用户归因的"先按 `` ` `` 再按 ESC"更像巧合。
4. **影响范围**：新旧实现同等再现（新 26% / 旧 38% 量级，样本较小，不宜下"旧更差"结论），属**历史存在**的问题，不是本次重构引入。
5. **量的解释（未验证）**：慢路径 11.5s 量级与"等待 LLM 首个数据块"的时长相符——推测中断信号已置位但响应链在"等首个数据"处阻塞，直到检查点生效才显示"已打断"；快路径则像"中断直接命中活跃请求句柄"的路径。该推测需要代码级插桩（E1 范围内）确证，本报告不作结论。
6. **未复现项**：未观察到"永久无法打断"；也未观察到按键被彻底丢弃（回合结束后的残留按键会进入输入框，如 `` ` `` 显示在提示符后）。

## 7. 边界与限制

- 实验为黑盒端到端；内部机制（中断置位时刻、句柄可关闭性）未见，仅能从屏幕/日志外部证据推断，故第 6.5 条标记「未验证」。
- 注入为程序化 `WriteConsoleInputW`，非物理键盘/输入法路径；时序比人手精确，但键序列形态与用户操作一致。
- 延迟量级可能与 LLM 服务端当时状态相关（网络首字节、负载）；本环境为同一网络同一密钥，结论对"延迟偶发且可达 10s 级"有效，对具体毫秒值不做保证。
- 每条序列 3 次（任务要求下限）；慢路径为低概率事件，3 次不足以给出稳定概率，报告中概率仅作量级参考。
- API 消耗：约 40 次"你好"短对话，均在私有密钥上正常完成。
